백엔드 품질은 API 코드 안에서만 결정되지 않는다. 배포가 부팅에서 죽지 않는지, 프론트가 API 계약을 확인할 수 있는지, 오류가 발생했을 때 팀이 빨리 알아차리는지도 운영 품질의 일부다.

Flown LMS에서 겪은 운영·협업 개선은 한 문장으로 묶을 수 있다.

> 실패를 숨기지 않고, 팀이 같은 상태를 보게 만든다.

## Flyway 부팅 장애

프로덕션 배포 후 애플리케이션이 부팅되지 않고 크래시 루프에 빠진 적이 있었다. 기능 하나가 실패한 것이 아니라 서버 자체가 올라오지 않는 문제라 영향이 컸다.

원인은 Flyway 마이그레이션 버전 갭이었다. 운영 DB의 마이그레이션 이력과 애플리케이션이 기대하는 마이그레이션 파일 흐름이 맞지 않아 부팅 단계에서 검증이 실패했다. 이 문제는 단순히 "파일 하나 수정"으로 끝낼 수 없었다. 운영 hotfix와 develop 반영이 모두 필요했다.

이 경험 이후 마이그레이션은 코드보다 더 조심해야 하는 변경으로 보게 됐다. 애플리케이션 코드는 롤백하거나 다시 배포할 수 있지만, DB 마이그레이션은 이미 운영 데이터와 연결된다. 그래서 버전 순서, 누락 여부, 운영 반영 경로를 배포 전에 확인하는 습관이 필요하다.

## Swagger 500 오류

팀 개발에서 Swagger 문서가 열리지 않는 것은 단순한 불편이 아니다. 프론트엔드가 API 계약을 확인할 수 없으면 병렬 개발이 막힌다.

`/v3/api-docs`가 500으로 죽는 문제를 추적했을 때 원인은 의존성 충돌이었다. `anthropic-java` 의존성이 끌고 온 `swagger-annotations`가 springdoc과 충돌하고 있었다. 해당 transitive dependency를 제외해 API 문서를 복구했다.

여기서 중요한 점은 "문서 페이지 하나 고쳤다"가 아니라, 팀이 API 계약을 확인하는 통로를 다시 열었다는 것이다. 협업 도구도 운영 품질의 일부다.

## Sentry로 오류를 표면화하기

오류를 사람이 로그에서 매번 찾아야 하는 구조는 늦다. 사용자가 신고하거나 누군가 우연히 로그를 보기 전까지 팀은 문제를 모를 수 있다.

그래서 Sentry를 붙여 예외가 발생하면 자동으로 표면화되게 했다. 결제 권한 지급 실패를 메트릭으로 드러낸 것과 같은 원칙이다. 실패는 조용히 사라지면 안 된다. 팀이 볼 수 있는 곳으로 올라와야 한다.

물론 알림은 많아질수록 피로해진다. 작은 프로젝트에서는 표면화 자체가 우선이었지만, 규모가 커지면 severity, sampling, ignore rule 같은 노이즈 관리가 필요하다.

## 진행 상황을 한곳에서 보기

팀 진행 상황이 여러 도구에 흩어져 있으면, 누가 무엇을 하고 있고 어떤 일이 막혔는지 파악하는 데 시간이 든다. 그래서 Jira 대시보드와 캘린더를 정리해 스프린트 일정과 진행 상황을 한 화면에서 볼 수 있게 했다.

이건 백엔드 코드 자체는 아니지만 팀이 같은 상태를 보게 만드는 작업이다. 같은 상태를 봐야 병목을 빨리 찾고, 일정과 구현 범위를 조정할 수 있다.

## 이 사례에서 남긴 것

Flyway, Swagger, Sentry, Jira는 서로 다른 도구처럼 보이지만 목적은 같았다. 팀이 문제를 늦게 발견하지 않게 하고, 같은 정보를 기준으로 움직이게 하는 것이다.

운영 품질은 "장애가 절대 안 난다"가 아니라, 장애가 났을 때 어디서 멈췄는지 빠르게 알고, 다음 배포에서 같은 문제가 반복되지 않도록 흐름을 바꾸는 데서 만들어진다.
