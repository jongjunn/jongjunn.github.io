> 온라인 강의 LMS(Flown)에서 결제·주문·환불 도메인을 맡으며 겪은 실제 버그와 그 보정 과정을 정리했다.
> 관련 커밋: `b42b97f2`(원인 수정 + 실패 표면화), `a21efc8f`(#675, 멱등 재시도 보정)

## 1. 문제 정의 — 결제에서 가장 무서운 상태

결제 기능에서 "결제가 실패했다"는 사실 별로 무섭지 않다. 사용자에게 실패라고 알려주고 다시 시도하게 하면 된다. 진짜 무서운 건 이거다.

> **PG 승인은 성공해서 사용자에게 돈은 빠져나갔는데, 우리 서비스에서는 아무것도 못 받는 상태.**

LMS의 다른 도메인(강의 목록, 진도 등)은 대부분 "부하를 어떻게 줄일까"가 관심사였다. 그런데 결제만은 성격이 달랐다. **한 번 어긋나면 사용자 신뢰가 바로 깨지고, 돈이 걸려 있어 조용히 넘어갈 수 없다.** 그래서 결제 도메인의 불변식을 이렇게 잡았다.

- 불변식: **과금이 확정됐다면, 사용자는 반드시 그에 해당하는 권한(구독권/수강권)을 받아야 한다.**

이 글은 그 불변식이 실제로 깨졌던 사건과, 그걸 어떻게 다시 세웠는지에 대한 기록이다. (범위: 결제 확정 후 권한 지급의 정합성. 비범위: PG 인증 흐름 자체.)

## 2. 증상 — "결제는 성공인데 구독이 없어요"

구독 결제를 확정했는데 구독이 생성되지 않는 현상이 있었다. 결제 확정 API는 정상 응답(성공)을 반환했다. 즉 **서버조차 "성공했다"고 착각하고 있었다.**

로그를 따라가니 구독 INSERT 지점에서 예외가 있었다.

```
Field 'subscription_id' doesn't have a default value
```

## 3. 원인 추적 — 표면 원인과 진짜 원인

**표면 원인:** `SubscriptionJpaEntity`는 PK를 `IDENTITY` 전략으로 쓰는데, 실제 DB 테이블 `subscriptions.subscription_id`에 `AUTO_INCREMENT`가 빠져 있었다. 그래서 INSERT 시 PK 기본값이 없어 실패했다. 토스 승인(과금)은 이미 끝난 뒤라, 구독만 생성되지 않고 결제는 확정된 채로 남았다.

여기서 두 가지를 더 팠다.

**(1) 같은 결함이 더 있지 않을까 — 전수 점검.**
`members`에서도 과거에 같은 결함(V3.5.2)이 있었다는 걸 알고 있었다. 그렇다면 "IDENTITY 전략인데 AUTO_INCREMENT가 없는" 테이블이 또 있을 수 있었다. 실제로 점검하니 `video_progress.progress_id`도 동일한 결함을 갖고 있었다. 지금 당장 터지지 않았을 뿐, 같은 사고를 기다리는 지뢰였다.

**(2) 진짜 원인은 따로 있었다 — 실패를 조용히 삼킨 코드.**
더 근본적인 문제는 결제 확정 서비스가 **권한 지급 실패를 무음으로 삼키고 결제만 성공으로 반환**하고 있었다는 점이다. 지급이 실패해도 아무도 몰랐다. 사용자도, 운영자도.

```java
// 결제(과금)는 이미 PG에서 확정됐으므로, 지급 실패는 주문을 되돌리지 않고
// 운영 알람용 ERROR 로그만 남긴다(수동 보정 대상).
private void dispatchAccessGrant(Order order) {
    try {
        // ... 구독권/수강권 지급 ...
    } catch (RuntimeException e) {
        // 결제는 이미 확정됐으나 지급만 실패한 상태 — 무음으로 삼키면
        // 사용자는 과금 후 아무것도 못 받는다. 실패를 표면화한다.
        meterRegistry.counter("order.payment.access_grant.failed",
                "type", order.getType().name()).increment();
        log.error("[ACCESS_GRANT_FAILED] 결제는 완료됐지만 지급 실패 — orderNo: {}", order.getOrderNo(), e);
    }
}
```

## 4. 조치 — 스키마 수정 + 실패 표면화 + 멱등 재시도

세 갈래로 고쳤다.

**① 스키마 결함 수정 (재발 방지).**
`V3.5.3` 마이그레이션으로 `subscriptions`와 `video_progress`의 PK에 `AUTO_INCREMENT`를 넣었다. 이때 `orders`/`order_items`(TABLE 제너레이터 사용)나 `subscription_plans`(시드로 PK 지정) 같은 테이블은 전략이 달라 **의도적으로 제외**했다. "전부 다 바꾸기"가 아니라 "같은 결함을 가진 것만" 고른 것이다.

**② 실패를 표면화.**
지급 실패를 `order.payment.access_grant.failed` 메트릭으로 올려 운영 알람이 뜨게 했다. **결제는 이미 확정됐으니 롤백(=환불)하지 않고, 수동 보정 대상으로 드러내는 쪽**을 택했다.

**③ 멱등 재호출에서 지급 재시도 (`a21efc8f`, #675).**
프론트가 결제 확인을 재호출하면, 주문이 이미 `PAID`라 기존 코드는 멱등 응답만 반환하고 지급을 다시 시도하지 않았다. 그래서 "결제는 끝났는데 권한은 없는" 상태가 그대로 굳었다. 이를 고쳐 **멱등 응답 경로에서도 `PAID` 주문에 한해 지급을 재시도**하도록 했다. 단, 이미 지급이 끝난 경우(`SUBSCRIPTION_ALREADY_ACTIVE` / `ENROLLMENT_ALREADY_EXISTS`)는 실패가 아니라 정상 종료로 처리해, 재시도가 반복 알람을 만들지 않게 했다.

## 5. 트레이드오프 — 왜 롤백하지 않았나

가장 고민한 결정은 "지급이 실패하면 결제를 롤백할까"였다. 롤백하지 않기로 했다.

- PG 승인은 **외부 시스템에서 이미 확정**된 사실이다. 이걸 롤백하려면 결제 취소(환불)를 다시 호출해야 하고, 그 취소가 또 실패할 수 있다. 실패를 실패로 덮는 구조가 된다.
- 대신 **"과금은 유지, 지급은 반드시 맞춘다"** 로 방향을 잡았다. 실패를 표면화하고, 멱등 재호출로 지급을 재시도한다.

이 선택은 "즉시 완벽한 자동 복구"를 포기하는 대신 **설명 가능하고 예측 가능한 상태**를 얻는다. 사용자 과금은 절대 임의로 건드리지 않는다는 원칙이 지켜진다.

## 6. 한계와 다음 단계 (정직하게)

- 현재 보정은 **멱등 재호출에 의존**한다. 재호출이 오지 않으면 지급은 메트릭 알람 → 수동 보정에 머문다.
- 자동 재처리 큐/outbox 패턴은 **아직 구현하지 않았다.** 다음 단계는 지급 실패 건을 별도 테이블에 적재하고 배치로 재처리하거나, outbox로 지급 이벤트를 보장하는 것이다.
- 실서비스 규모의 장애 통계(발생률 등)는 없다. 이 글은 "대규모 장애 대응기"가 아니라 "결제 정합성 버그를 원인부터 재발 방지까지 닫은 기록"이다.

## 7. 채용 관점에서 강조하고 싶은 점

이 글의 강점은 결제 사고를 "운이 나빴다"로 끝내지 않고, 같은 계열의 스키마 결함을 전수 점검한 점이다. 하나의 오류를 고친 뒤 `video_progress`까지 확인한 과정은 문제를 국소 패치로만 보지 않는 태도를 보여준다.

동시에 아직 자동 복구 큐가 없다는 한계도 숨기지 않았다. 과금과 권한 지급 사이의 불일치는 사용자가 바로 체감하는 문제이므로, 현재 닫은 범위와 다음에 닫아야 할 범위를 분리해 말하는 것이 신뢰를 만든다고 봤다.

## 8. 배운 것

- **결제에서 가장 위험한 건 실패가 아니라 "조용한 성공"이다.** 예외를 삼키면 사고가 숨는다. 실패는 반드시 표면화돼야 한다.
- **한 번의 버그는 같은 결함의 신호일 수 있다.** `subscriptions`에서 발견한 결함이 `video_progress`에도 있었다. 하나 고칠 때 "이 결함의 계열"을 전수 점검하는 습관이 재발을 막는다.
- **외부 시스템이 이미 확정한 상태는 함부로 되돌리지 않는다.** 롤백보다 "표면화 + 보정"이 더 안전할 때가 있다.
