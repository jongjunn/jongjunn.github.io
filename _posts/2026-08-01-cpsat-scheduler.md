> Flown LMS의 Python AI 서버에서 개인화 학습 스케줄러를 구현한 기록.
> 관련 코드: `Python-Server/domain/scheduler.py` (본인 작성), 복습은 `domain/review.py`(FSRS)

## 1. 문제 정의 — "그냥 나눠주면" 안 되는 이유

목표는 **개인화된 학습 스케줄러**였다. 수능까지 남은 기간 안에, 여러 과목의 강의를 주차별로 배치해주는 것이다.

처음엔 단순하게 접근할 수도 있었다. "강의를 섹션(구간)별로 나눠서 주차에 분배"하는 방식. 하지만 이건 결국 **값을 균등 분할하고 카테고리로 분류하는 수준**에 그친다. 실제로는 아래 조건들이 **동시에** 맞아야 한다.

- 각 강의는 자기 **마감 주차(deadline)** 전에 끝나야 한다
- 주차마다 **학습 가능 시간(cap)** 을 넘으면 안 된다
- **과목별로도** 한 주에 특정 과목이 몰리면 안 된다
- **선수 강의**가 후속 강의보다 앞 주차에 있어야 한다
- 그러면서 **취약 과목(등급 낮은)** 은 더 이른 주차에 배치하고 싶다

이 조건들을 단순 분할 로직으로 동시에 만족시키려면, 조건 하나 추가할 때마다 if가 폭발하고 서로 충돌한다. 그리고 **"이 기간 안엔 도저히 못 끝낸다(완주 불가)"** 는 것을 단순 분할은 깔끔하게 판단하지 못한다.

그래서 **제약 충족 문제(constraint satisfaction)** 로 보고 OR-Tools **CP-SAT**로 모델링했다. 조건을 "코드로 계산"하는 게 아니라 "제약으로 선언"하면, solver가 그걸 동시에 만족하는 해를 찾아준다.

## 2. 설계 — 제약을 선언으로 옮기기

**결정변수**: 강의 × 주차를 Boolean으로. `x[(lesson, w)] = 1`이면 그 강의를 그 주에 한다.

```python
x[(lesson["id"], w)] = model.NewBoolVar(f"x_{lesson['id']}_{w}")
# 각 강의는 정확히 한 주에 배정된다 (마감 주차 이하 범위에서만 변수 생성)
model.AddExactlyOne(x[(lesson["id"], w)] for w in range(num_weeks) if (lesson["id"], w) in x)
```

**주차별 용량 제약**: 그 주에 배정된 강의 시간 합이 그 주 cap을 넘지 않게.

```python
model.Add(sum(lesson["duration_min"] * x[(lesson["id"], w)] for ...) <= weekly_caps[w])
```

**과목별 주간 상한**: 전체 cap과 별개로, 한 과목이 특정 주에 쏠리는 것을 막는다.

**선수관계 제약**: 선수 강의의 주차 ≤ 후속 강의의 주차.

```python
model.Add(week_of[pre_id] <= week_of[post_id])
```

**목적함수**: 취약 과목을 이른 주차로. 등급 가중치 × 주차 인덱스의 합을 최소화하면, 가중치가 큰(취약한) 과목일수록 낮은 주차 인덱스로 당겨진다.

```python
# minimize Σ grade_weights[course] * w * x  → 취약 과목이 앞 주차로 배치되는 soft preference
```

**완주 불가 판정**: solver가 OPTIMAL/FEASIBLE을 못 내면 `None`을 반환한다. 이게 단순 분할과의 결정적 차이다. **"제약을 다 만족하는 배치가 존재하지 않는다"** 를 명확히 알 수 있고, 호출부는 이걸 받아 기간 연장 재시도 → 최종적으로 "이 기간엔 완주 불가" 알림으로 잇는다.

```python
solver.parameters.num_search_workers = 4
status = solver.Solve(model)
if status not in (cp_model.OPTIMAL, cp_model.FEASIBLE):
    return None  # 완주 불가
```

## 3. 개인화와 고도화 — 시간이 지날수록 정교해지게

정적인 한 번의 배치로 끝내고 싶지 않았다. 두 가지로 개인 데이터를 반영한다.

- **학습 효율 계수**: 실제 학습 시간 / 예상 학습 시간 비율로 개인 속도를 추정해 cap에 반영한다. 표본이 적으면(3개 미만) 1.0으로 두고, 과도한 출렁임을 막기 위해 0.5~2.0으로 clamp한다.
- **복습은 FSRS로**: 복습 일정은 별도로 `review.py`에서 FSRS(간격 반복) 라이브러리를 써서, 퀴즈 점수(Rating)에 따라 다음 복습일(due)을 갱신한다. 사용자의 반응이 쌓일수록 복습 간격이 개인화된다.

즉 **CP-SAT는 "이번 기간의 배치"를, FSRS는 "반복 학습의 타이밍"을** 맡아, 데이터가 쌓일수록 스케줄이 정교해지는 구조를 노렸다.

## 4. 검증

도메인 테스트로 solver의 동작을 고정했다(전부 본인 작성).

- 단순 분할 방식이면 실패할 수 있는 케이스에서 **통합 CP-SAT 배치가 성공**하는지
- 과목별 cap, 마감, 선수관계가 실제로 지켜지는지
- **INFEASIBLE(완주 불가)** 케이스가 제대로 None으로 떨어지는지
- 수능일 버퍼·연장 계산 경계값

## 5. 트레이드오프

- **표현력 vs 복잡도**: CP-SAT는 조건을 선언적으로 다 넣을 수 있는 대신, 모델링을 잘못하면 의도치 않게 INFEASIBLE이 나거나 solver 시간이 늘 수 있다. 그래서 `num_search_workers`를 두고, 제약을 hard(마감·cap·선수)와 soft(취약과목 우선, 목적함수)로 구분했다.
- **최적 vs 실용**: 반드시 전역 최적해가 필요한 문제는 아니라, OPTIMAL이 아니어도 FEASIBLE이면 채택한다. "완벽한 배치"보다 "제약을 다 지키는 배치"가 목적이었다.

## 6. 한계 (정직하게)

- 이 스케줄러가 **실제 학습 성과를 올렸다는 A/B 결과는 없다.** 성과 수치로 말하지 않는다. 이 글은 "제약을 코드로 모델링하고 완주 가능성을 판정하는 백엔드 기능"에 대한 기록이다.
- FSRS는 **직접 구현한 알고리즘이 아니라 라이브러리 사용**이다. 내가 한 건 퀴즈 점수를 Rating으로 매핑하고 도메인에 배선한 부분이다.
- 이탈위험 점수(`risk.py`)는 rule-based이며 CoxPH 같은 예측 모델이 아니다. 이 글에서 다루지 않는다.

## 7. 채용 관점에서 강조하고 싶은 점

이 글은 "AI를 했다"는 포장보다, 복잡한 요구사항을 제약 모델로 바꾸는 문제 분해 능력을 보여주기 위한 글이다. 조건이 늘어날수록 if 분기보다 결정변수·hard constraint·soft objective로 나누는 편이 유지보수 가능하다고 판단했다.

인사 관점에서는 성과 수치를 만들지 않고 A/B 미측정을 명시한 점이 신뢰 신호다. 개발자 관점에서는 CP-SAT가 풀어야 할 제약, FEASIBLE/INFEASIBLE 처리, FSRS와의 역할 분리가 코드로 설명 가능한지에 초점을 맞췄다.

## 8. 배운 것

- **조건이 3개를 넘어 서로 충돌하기 시작하면, "계산"보다 "제약 선언"이 낫다.** if로 푸는 대신 solver에게 맡기니 조건 추가가 선형적으로 쉬워졌다.
- **"불가능"을 판정할 수 있는 게 큰 가치다.** 단순 분할은 억지로 답을 내지만, 최적화는 "이 기간엔 해가 없다"를 알려준다. 그게 사용자에게 정직한 알림으로 이어졌다.
