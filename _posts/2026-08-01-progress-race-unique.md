> Flown LMS에서 학습 활동(영상 진도) 저장 경로의 동시성 버그를 추적·수정한 기록.
> 관련 커밋: `71a059c5` / 마이그레이션 `V3.5.5`

## 1. 문제 정의

영상 진도 저장의 불변식은 단순하다.

> **한 회원의 한 영상 진도는 DB에 정확히 1행이어야 한다. — `(member_id, video_id)`는 유일하다.**

이 불변식이 코드(애플리케이션)에만 있고 **DB 제약으로는 없었다.** 그 틈에서 동시성 버그가 났고, 한 번 깨지자 해당 회원+영상의 재생과 진도 저장이 **영구적으로** 실패했다. (범위: 진도 저장/조회의 정합성. 비범위: 영상 스트리밍 자체.)

## 2. 증상

특정 회원이 특정 영상에서 재생(`GET /videos/{id}/play`)과 진도 저장(`PATCH .../progress/position`)이 계속 500으로 실패했다. 일시적 오류가 아니라 **그 조합에서는 될 때까지 안 되는** 영구 실패였다.

처음 이상을 눈치챈 건 UI였다. **진도가 화면에 제대로 표시되지 않아서** "표시 버그인가?" 하고 확인하러 들어갔는데, 프론트 문제가 아니라 **해당 API가 아예 500으로 죽고 있었다.** 거기서부터 서버·데이터를 파고들었다.

## 3. 원인 추적

로그의 예외는 `NonUniqueResultException`이었다. 조회 코드는 이랬다.

```java
Optional<VideoProgress> findByMemberIdAndVideoId(...)
```

`Optional`은 "0개 또는 1개"를 전제한다. 그런데 실제 테이블에는 **같은 `(member_id, video_id)` 행이 여러 개** 있었다. 그래서 조회가 터졌고, 조회가 터지니 재생도 진도 저장도 전부 실패했다.

그럼 중복행은 왜 생겼나?

- `video_progress`에 `(member_id, video_id)` **유니크 제약이 없었다.**
- **첫 시청 시 동시 요청**이 들어오면, 두 요청 모두 "진도 없음"으로 읽고 **각자 INSERT** → 중복행. 전형적인 read-then-write 레이스 컨디션이다.

여기서 두 가지를 더 발견했다.

**(1) 테스트가 버그를 "정상"으로 굳히고 있었다.**
어댑터 테스트가 이미 `(1, 10)` 행이 있는데 같은 조합으로 새 행이 생기는 것을 **정상으로 단언**하고 있었다. 즉 중복 생성이 스펙처럼 고정돼 있어서, 이 테스트가 초록불인 한 아무도 버그를 눈치채지 못했다.

**(2) 그 테스트들은 사실 제대로 돌지도 않았다.**
Flyway가 H2 환경에서 MySQL 전용 `V1__baseline.sql`을 실행하려다 컨텍스트 로딩 단계에서 전부 실패하고 있었다. 스키마는 `@Sql`로 넣고 있었으므로 Flyway를 꺼야 했다.

## 4. 조치

**① 데이터 정리 + 유니크 제약 (V3.5.5).**
기존 중복행을 정리하고 `(member_id, video_id)` 유니크 제약을 추가했다. 정리 시 아무 행이나 남기지 않고 **완료 > 시청시간 > 재생위치 순으로 가장 많이 진행된 행**을 남겨 진도 손실을 막았다.

**② 첫 INSERT를 별도 트랜잭션으로 분리 (`REQUIRES_NEW`).**
유니크 제약을 걸면 경합에 밀린 요청은 제약 위반으로 실패한다. 이걸 500으로 터뜨리는 대신 **"기존 행을 읽어 갱신"으로 복구**해야 한다. 그래서 INSERT를 `VideoProgressInserter`(REQUIRES_NEW)로 분리했다.

```java
// 동시 INSERT가 같은 (member_id, video_id)에 걸리면 한쪽은 유니크 제약 위반.
// 바깥 트랜잭션에서 그대로 터뜨리면 rollback-only로 오염돼 복구를 할 수 없다.
// REQUIRES_NEW로 실패를 이 트랜잭션 안에 가둔다. saveAndFlush로 즉시 flush해 호출부가 잡게 한다.
@Transactional(propagation = Propagation.REQUIRES_NEW)
public VideoProgressJpaEntity insert(VideoProgressJpaEntity entity) {
    return repository.saveAndFlush(entity);
}
```

**③ 복구 읽기도 반드시 `REQUIRES_NEW` (여기가 핵심 함정이었다).**
제약 위반 후 "먼저 커밋된 행"을 읽어 갱신해야 하는데, **바깥 트랜잭션에서 읽으면 그 행이 안 보인다.** MySQL 기본 격리수준 REPEATABLE READ에서는 스냅샷이 **첫 조회 시점**에 고정되기 때문이다. 경합 상대가 그 뒤에 커밋한 행은 내 스냅샷에 없다 → 복구 실패 → 유니크 위반이 그대로 상승.

그래서 복구 읽기도 새 트랜잭션(=새 스냅샷)에서 해야 방금 커밋된 행을 확실히 본다.

```java
// 새 트랜잭션=새 스냅샷에서 읽어 방금 커밋된 행을 본다.
// 그래도 없으면 진짜 제약 위반(NOT NULL·FK 등)이므로 empty를 돌려 원래 예외를 던지게 한다.
@Transactional(propagation = Propagation.REQUIRES_NEW)
public Optional<VideoProgressJpaEntity> updateExisting(...) { ... }
```

**④ 테스트 교정.**
버그를 스펙으로 굳힌 단언을 고치고 중복 방지 테스트를 추가했다. H2에서 죽던 Flyway는 끄고 `@Sql`로 스키마를 넣었다.

## 5. 검증

MySQL 8에 중복행을 일부러 만들었다(3행/2행). `V3.5.5` 적용 후:

- 조합당 **1행만** 남음
- 남은 행은 **가장 많이 진행된 행** (진도 손실 없음)
- 이후 중복 INSERT는 `ERROR 1062`(duplicate)로 차단됨

## 6. 트레이드오프와 한계

- `REQUIRES_NEW`는 별도 커넥션/트랜잭션을 쓰므로 비용이 있다. 하지만 "경합에 밀린 요청도 500 없이 복구"라는 정합성·사용자 경험을 위해 감수했다.
- 근본 방어는 애플리케이션 조건문이 아니라 **DB 유니크 제약**이다. 앱 레벨 "있나 확인 후 INSERT"는 레이스에 취약하다는 걸 이 버그로 체감했다.
- 한계: 정리 우선순위(완료>시청시간>재생위치)는 도메인 판단이다. 다른 도메인에선 다른 기준이 맞을 수 있다.

## 7. 이 사례에서 남긴 것

이 버그는 화면 이상에서 출발했지만, 프론트 표시 문제가 아니라 서버 API와 데이터 불변식 문제로 좁혀 갔다. 사용자에게는 "진도가 안 보인다"는 작은 불편처럼 보이지만, 서버 입장에서는 특정 회원과 영상 조합이 영구 실패하는 정합성 사고였다.

개발자 관점에서는 유니크 제약, 마이그레이션 데이터 정리, `REQUIRES_NEW`, MySQL REPEATABLE READ를 하나의 복구 흐름으로 연결한 점이 핵심이다. 인사 관점에서는 테스트가 잘못된 동작을 정상으로 고정하고 있었다는 불편한 사실까지 인정하고 고친 점을 강조하고 싶다.

## 8. 배운 것

- **애플리케이션에만 있는 불변식은 동시성에서 깨진다.** "유일해야 한다"는 규칙은 DB 제약으로 내려야 한다.
- **초록불 테스트가 버그를 지켜줄 수 있다.** 테스트가 잘못된 동작을 정상으로 단언하면, 그 테스트는 안전망이 아니라 자물쇠다.
- **격리수준은 교과서가 아니라 복구 코드에서 만난다.** REPEATABLE READ 스냅샷 때문에 "방금 커밋된 행이 안 보이는" 상황을, 복구 경로를 짜다가 실제로 밟았다.
