> Flown LMS 결제 도메인에서 외부 PG 호출과 DB 트랜잭션의 경계를 잡은 기록.
> 관련 코드: `PaymentFacade`, `ConfirmOrderPaymentService`(본인 작성)

## 1. 문제 정의

결제 확정은 "DB 저장 + 외부 PG 호출"이 섞인 작업이다. 여기서 순진한 구현은 이렇게 된다.

```
@Transactional {
  주문 저장
  pgClient.confirm(...)   // 외부 네트워크 호출 — 수백 ms~수 초
  주문 상태 PAID로 변경
}
```

문제는 **PG 응답을 기다리는 내내 DB 커넥션을 잡고 있다**는 점이다. PG가 느려지면 트랜잭션이 길어지고, 동시 결제가 몰리면 **커넥션 풀이 고갈**돼 결제와 무관한 API까지 함께 죽는다.

> 그래서 원칙: **외부 시스템 호출은 DB 트랜잭션 밖에 둔다. DB 트랜잭션은 짧게 유지한다.** (범위: 결제 승인의 트랜잭션 경계. 비범위: PG 내부 처리.)

## 2. 설계 — 트랜잭션을 쪼개고 PG를 그 사이에 둔다

`PaymentFacade`에는 이 의도가 주석으로 명시돼 있다. 저장소 메서드를 각각 독립 `@Transactional`로 두어, **PENDING 저장(커밋) → PG 호출(트랜잭션 밖) → confirm/fail 저장(커밋)** 순서로 흐르게 했다.

```
createPending()   // @Transactional 커밋 — 짧게
pgClient.confirm(...)   // 트랜잭션 밖에서 외부 호출
confirmPayment()  // @Transactional 커밋 — 짧게
```

주문 결제 경로(`ConfirmOrderPaymentService`)도 같은 원칙이다. Redis 락으로 동시성을 막은 뒤, PG confirm은 트랜잭션 밖에서 호출하고, 성공하면 `markPaid`로 **짧은 트랜잭션**만 커밋한다. DB 커넥션은 PG 응답을 기다리는 동안 점유되지 않는다.

## 3. 트레이드오프 (이 글의 핵심)

경계를 이렇게 그으면 **얻는 것과 잃는 것**이 분명하다.

- **얻는 것**: PG 호출 동안 DB 커넥션 미점유 → 커넥션 풀 고갈 위험 감소, 트랜잭션 짧음.
- **잃는 것**: "PG는 성공했는데 그 직후 DB 저장/권한 지급이 실패"하는 창이 생긴다. 이건 한 트랜잭션으로 묶여 있지 않으므로 자동 롤백되지 않는다.

즉 **원자성(하나로 묶기)을 포기하는 대신 커넥션 효율을 얻는** 선택이다. 그리고 포기한 원자성은 **보정으로 메꿔야** 한다.

## 4. 포기한 원자성을 어떻게 메꿨나

실제로 이 "PG 성공 후 DB/지급 실패" 창에서 사고가 났었다(과금은 됐는데 구독 미생성). 그래서 두 가지로 보정한다.

- **실패 표면화**: 지급 실패를 삼키지 않고 metric/로그로 올려 수동 보정 알람이 뜨게 한다.
- **멱등 재시도**: 재호출 시 `PAID` 주문에 한해 지급을 재시도하고, 이미 지급된 경우는 정상 종료로 본다.

(자세한 사고 분석은 "과금은 됐는데 구독이 안 생긴 버그" 글로 이어진다.)

## 5. 한계와 다음 단계

- 현재 보정은 표면화 + 멱등 재호출에 의존한다. 완전 자동 복구를 위해 **outbox/재처리 큐**로 지급을 보장하는 것이 다음 단계다.
- "외부 성공 + 내부 실패"의 근본 해법 중 하나인 **거래 대사(reconciliation)** 배치도 후속 과제다.

## 6. 이 사례에서 남긴 것

이 글은 결제 로직을 "트랜잭션 하나로 묶으면 안전하다"는 단순한 답에서 멈추지 않는다. 외부 호출을 트랜잭션 안에 넣으면 원자성처럼 보이지만, 실제 운영에서는 커넥션 점유와 장애 전파라는 비용이 생긴다. 그 비용을 인식하고 경계를 나눈 판단을 설명하려 했다.

인사 관점에서는 사용자 결제 흐름을 안정적으로 유지하려는 책임감, 개발자 관점에서는 트랜잭션 경계·락·보정 책임을 분리해 설명할 수 있는지가 핵심이다. 아직 outbox와 대사 배치가 없다는 점은 기능을 부풀리지 않기 위해 한계로 남겼다.

## 7. 배운 것

- **외부 호출을 트랜잭션 안에 넣는 건 편하지만, 커넥션 점유라는 비용을 숨긴다.** 경계를 밖으로 빼는 순간 원자성을 잃고, 그 대가로 보정 설계가 필요해진다.
- **"트랜잭션을 어디서 끊을까"는 성능과 정합성의 트레이드오프 결정**이지, 정답이 하나인 문제가 아니다.
