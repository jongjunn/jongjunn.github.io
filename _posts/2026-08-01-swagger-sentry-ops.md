> Flown LMS 팀 개발에서 API 문서·오류 가시성·진행 상황 공유를 개선한 기록.
> 관련 커밋: `60ad8660`(/v3/api-docs 500 해결) 외 Sentry 설정

## 1. 문제 정의

팀으로 백엔드를 개발하면 코드 외에 **협업 인프라**가 병목이 된다. 세 가지가 문제였다.

- **API 문서(Swagger)가 열리지 않았다.** 프론트가 API 계약을 확인할 창구가 막히면 병렬 개발이 멈춘다.
- **오류를 매번 로그를 뒤져 수동으로 확인**해야 했다. 문제가 났는지조차 늦게 안다.
- **팀 진행 상황이 여러 도구에 흩어져** "누가 뭘 하는지" 파악이 안 됐다.

이건 "기능 구현"이 아니라 **팀이 막히지 않게 하는 일**이라 조직 적합성과 직접 닿는다.

## 2. Swagger 500 오류 수정

API 문서 엔드포인트 `/v3/api-docs`가 **500으로 죽어** 문서가 아예 열리지 않았다. 추적해 보니 원인은 의존성 충돌이었다. **`anthropic-java` 의존성이 끌고 온 swagger-annotations**가 springdoc과 충돌하고 있었다. 해당 transitive 의존성을 빌드에서 제외해 `/v3/api-docs`를 복구했다(`60ad8660`).

> 포인트: "문서가 안 열린다"는 프론트 입장에선 계약 확인 불가 = 작업 중단이다. 이걸 빌드 의존성 레벨에서 원인을 찾아 고쳤다.

## 3. Sentry로 오류 자동 표면화

Swagger를 고치면서 든 생각은 "오류를 사람이 매번 찾는 구조 자체가 비효율"이라는 것이었다. 그래서 **Sentry 오류 알림을 붙여**, 예외가 발생하면 로그를 뒤지지 않아도 **자동으로 표면화**되게 했다. 문제 인지 시점을 "누가 신고할 때"에서 "발생 즉시"로 당겼다.

이 태도는 결제 도메인에서 지급 실패를 metric으로 표면화한 것과 같은 원칙이다 — **실패는 숨기지 말고 드러나게 한다.**

## 4. 진행 상황 대시보드 통합

팀 진행 상황을 통제하는 현황판이 여러 곳으로 나뉘어 있어 "누가 뭘 하고, 뭘 해야 하는지"가 한눈에 안 들어왔다. 그래서 **지라(Jira) 대시보드 하나로 통합**했다 — 일정을 대시보드에 띄우고, 스프린트를 캘린더에 반영하고, 흩어져 있던 통제 현황판을 한 화면으로 모았다. "상태를 찾으러 여러 곳을 도는" 비용을 줄이는 게 목적이었다.

## 5. 트레이드오프와 한계

- Sentry 같은 알림은 **노이즈 관리**가 관건이다. 모든 예외를 다 올리면 알람 피로가 생긴다. (현재 프로젝트 규모에선 표면화 우선이 맞았지만, 운영 규모에선 심각도·샘플링 기준이 필요하다.)
- 대시보드 통합은 팀 운영 개선이지 백엔드 코드 자체는 아니다. 이력서/블로그에선 "협업·운영 감각"으로만 포지셔닝하고, 기획 성과처럼 부풀리지 않는다.

## 6. 이 사례에서 남긴 것

이 글은 기술 심사보다 인사·협업 관점의 비중이 큰 글이다. Swagger 500을 고친 것은 단순히 문서 페이지 하나를 살린 일이 아니라, 프론트엔드가 API 계약을 확인하고 병렬로 움직일 수 있게 한 일이다. Sentry와 대시보드 정리도 같은 맥락에서 "팀이 문제를 더 빨리 보고 같은 상태를 보게 하는" 개선이었다.

개발자 관점에서는 의존성 충돌 원인 추적과 Sentry 도입의 한계가 평가 포인트다. 인사 관점에서는 팀 병목을 자기 일로 보고, 오류와 진행 상황을 숨기지 않고 표면화하려는 태도가 핵심이다.

## 7. 배운 것

- **협업 도구의 품질이 곧 팀 속도다.** 문서가 안 열리고 오류를 늦게 아는 것은 개인 실수가 아니라 팀 병목이다.
- **실패를 자동으로 드러내는 것**은 결제든 API든 같은 원칙이다.
